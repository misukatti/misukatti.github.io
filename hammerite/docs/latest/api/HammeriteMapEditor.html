HammeriteMapEditor

Editor. Inherits PanelContainer

The in-game level editor: a Control that edits a HammeriteMap through the game's own HammeriteMap3D, and the object games and addons extend it through.

Get one from HammeriteEditor.integrate(), which puts it in the tree, then set map_3d before map and show or hide it with activate() and deactivate(). The host owns the key that toggles it, and should ask prompt_unsaved_changes() before quitting. The seams a game or addon extends it through: entity types (register_point_entity_type(), extend_point_entity_type() and their brush counterparts), property controls (register_property_editor(), register_property_choices(), register_brush_property_editor(), register_brush_property_choices()), register_runtime_panel(), register_cell_overlay(), add_toolbar_button(), add_right_panel(), register_manual_section(), register_manual_pages(), and commands for menu items and keys. They may be called before the editor is in the tree. How they are named, and undone. register_* stores a definition, named by an id or a pair the caller chose, and unregister_* takes it away by the same; add_* puts a node in the editor, and remove_* takes that node back - so keep what an add_* returns, or the control it was handed. Every seam has its inverse, so an addon can undo all of what it did. Most of its other methods are what the editor's own menu commands and tools call - selection verbs, start_*_tool, toggles - and log their outcome to the editor's message log rather than returning it. Those are marked experimental: free to change, and not for a host to call.

canvas

var canvas: HammeriteEditorCanvas = null

The layer the editor is drawn on, and the authority on how big it is drawn. Null when something built the editor itself rather than through HammeriteEditor.integrate() - the tests do, and nothing here may assume it is there. Setting it is what wires the scale in both directions, because there is more than one way for the scale to change and only one of them came through ui_scale: the View menu's bigger and smaller call HammeriteEditorCanvas.step() straight on the canvas. Listening to the canvas catches every route rather than the one that happens to go through this class - which is why the remembered scale was written by the property and never by the menu, and so never came back.

suggest_ui_scale()

func suggest_ui_scale(scale: float) -> void

What the HOST thinks the editor should be drawn at - its own UI-scale setting, usually. A suggestion rather than an assignment, and the difference is the whole point: the host reads its settings file on the first frame and tells the editor a frame after that, which lands AFTER the remembered scale has been restored and puts the project's answer back over the person's. Told this way, the host's answer is the starting point on a machine where nobody has chosen, and is quietly ignored on one where somebody has. A host reacting to its setting actually CHANGING should assign ui_scale instead. That is somebody moving a slider now, and it should win.
