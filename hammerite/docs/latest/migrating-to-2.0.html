Migrating to Hammerite 2.0

Migrate a 1.x project before you open it in 2.0. Every .tres, .res and scene that 1.x saved names Hammerite's objects by the scripts they were - res://addons/hammerite-core/scripts/resources/map.gd, brush.gd, map_3d.gd and the rest - and 2.0 has none of those scripts: no stub at their paths, and no loader that reads such a file as the native classes. Until it is migrated a file naming one does not load at all. Godot says Failed loading resource: res://addons/hammerite-core/scripts/resources/map.gd for each script it names, and then the same of the file, so a map, a bake, a prefab set or a scene placing a HammeriteMap3D comes back null and the game does not start.

  1. Commit the project, or copy it.
  2. Install 2.0 in place of 1.x: every addon folder, with its library (What 2.0 needs).
  3. Migrate it: tools/migrate_to_2.sh path/to/project, from the release's docs zip, or Project → Tools → Migrate Hammerite 1.x Resources... in the Godot editor with the full package (Migrating a project). Opening the project first writes nothing by itself, but when the Godot editor offers to open a scene with missing dependencies anyway, or to fix them, decline: a scene saved that way has lost what it held of Hammerite's.
  4. Change the code 2.0's API breaks: the rest of this page.

What needs nothing: a .hmap saved by any earlier Hammerite opens, and so does every other data file - a .hcache worldrep or navigation cache, a variant's bake, the editor's .hworkspace and its autosaves. They name classes, not scripts, and read as they did.

Caches are migrated with the rest, and one that is not is only a cache. level.worldrep.res and level.nav.res, which 1.x wrote beside a map saved as a .res, fail to load as anything else 1.x saved does - with the same errors, on every load - and are then treated as missing: the world is compiled from the map and its navigation built again, and both are written in 2.0's form the next time the editor saves the map. Migrate them, or delete them, rather than leave them to print errors. Hammerite writes nothing else of its own under user://: the editor's workspace and autosaves are data files, and the lightmapper's diagnostic reports are never read back. What a game keeps there itself - its players' maps saved as .res, say - is migrated by pointing the editor's dialog at that folder, or by running the command on it. A game can call HammeriteMigration.migrate("user://maps") itself, but the class is experimental: it may change in any 2.x release, where the command and the menu items will not.

The rest of this page is what changed. 2.0 moves the addons' classes from GDScript into the native library (#263). A class keeps its name, its base class and what it does - checked against its script, call for call, before the script was deleted - but a native class cannot express everything a script could, and where it cannot, the API changes. Every such change is here, and every change of behaviour.

What 2.0 needs

  • The native library, always. 1.x ran on GDScript and used its native kernel where one was built; 2.0's classes are the library. It is addons/hammerite-core/bin/libhammerite.<platform>, loaded by hammerite_core.gdextension for all four addons, and there is no GDScript to fall back on: a project without it does not load core, and says "Hammerite's native library is not loaded". No native_* switch chooses any more (the kernel's classes and switches).
  • One of two packages, installed whole (#273). hammerite-runtime-<version>.zip is core, audio and nav, for a game whose players never open the map editor; hammerite-full-<version>.zip is those and the editor. 1.x's four addons were installed one by one; 2.0's come as a package's folders with the library built for exactly those, so replace all four 1.x folders with one package's. A hammerite-editor folder beside the runtime package's library has none of its classes, and a full library without one is missing a folder: either is an error as the project starts. An addon a game does not use stays installed with its plugin disabled. See Installing.
  • macOS, Linux x86_64 and Windows x86_64. A release carries the library for macOS as one universal binary (Apple silicon and Intel), for Linux x86_64 and for Windows x86_64, in every package. The .gdextension also names a Linux arm64 library, which a checkout can build (tools/build_native.sh) but no release carries.
  • No web export. No library is built for the web, and without one core does not load, so a game exporting to the web cannot use 2.0. None will be until GDExtension on the web is dependable (#263). 1.x did not support the web either, but nothing stopped its GDScript loading there.
  • Godot 4.7, as 1.x. The library is built against godot-cpp's 4.5 API and its .gdextension loads in 4.5 or later, but the suites run on 4.7.1 and nothing earlier is tested.
  • No hot reload. The library is not reloadable: restart the Godot editor after replacing it.

Migrating a project

Migrate a project once, after installing 2.0, from the command line or from either editor:

tools/migrate_to_2.sh path/to/project --dry-run   # what would change; writes nothing
tools/migrate_to_2.sh path/to/project             # migrate, keeping each original as <file>.bak
tools/migrate_to_2.sh path/to/project --no-backup # without the .bak files

The tool is not in either package, which hold only what goes into addons/: it is in tools/ of hammerite-docs-<version>.zip, released beside them, and of this repository. Unzip the docs anywhere and run it from there, naming the project - path/to/hammerite-docs/tools/migrate_to_2.sh path/to/project - keeping migrate_to_2.sh and migrate_to_2.gd together. It is a bash script, so on Windows run it from Git Bash, or use the editor's command below. It runs Godot headless in the project - /Applications/Godot.app unless GODOT= names another binary, as it must on Linux and Windows - importing it first if the project has not been opened since 2.0 was installed - and calls HammeriteMigration.migrate("res://"). It lists each file it migrated, with the classes it was migrated for, and each it could not, with why, and exits 1 when there is any of those. Commit the project, or copy it, before running it.

The editor does the same, with the dry run shown before anything is written: Project → Tools → Migrate Hammerite 1.x Resources... in the Godot editor, which rescans the project afterwards and is the one to use while the game cannot start, and File → Migrate 1.x Resources… in Hammerite's editor, in the game. Each lists what it would migrate and what it cannot, with why, migrates on confirming - keeping the .bak files unless told not to - and lists what it did. It looks in res:// and takes another res:// or user:// folder, such as where a game keeps its players' maps. Both are the editor's, so the full package has them and the runtime package does not: with the runtime package, use the command line. It migrates what core, audio and nav saved, and reports a file naming one of the editor's scripts - a scene placing an editor node, or the editor's settings saved as a .tres - as skipped, with its classes, for the full package to migrate.

What 2.x promises is the command and the two menu items - tools/migrate_to_2.sh with its options, File → Migrate 1.x Resources… and Project → Tools → Migrate Hammerite 1.x Resources... - and what they migrate (API stability). HammeriteMigration, the class all three call, and the editors' dialog are experimental: a script can call them, but they may change in any release.

What it does to a file that names a 1.x script of Hammerite's, and nothing else:

  • each object the file holds as a Resource carrying a 1.x script - a map, a brush, a bake, a probe set, a light curve, a prefab, an audio graph, a navigation cache - is written as its native class, without the script;
  • in a text scene (.tscn), each node carrying one of Hammerite's 1.x node scripts - map_3d.gd, eye_adaptation_3d.gd, a light, a decal, a mover, a trigger, a logic entity, an entity base, audio's emitter, receiver and sound entities, nav's link entity - is that node class, without the script or the _custom_type_script the editor marked it with, keeping its place and its properties;
  • the scripts go from the file's [ext_resource] lines or external table, and load_steps and the script class of the file's main resource with them.

Every other byte of the file is as it was: text stays text, binary stays binary, and a compressed .res is compressed again as it was, with its uid. The file is rewritten where it lies rather than loaded and saved, so nothing in the project is loaded - a game's own script that does not compile in a headless run would otherwise cost the objects carrying it their values - and the rewritten file is read back before it is kept. A file naming no 1.x script is not touched, nor is anything in a hidden folder, one holding a .gdignore, or Hammerite's own folders under addons/. A second run finds nothing to do.

A file it cannot migrate it leaves as it was, and says why:

  • it names a script of Hammerite's that has no class in 2.0. hammerite-audio's acoustic classes (acoustic_node_graph.gd and the rest) were renamed to its audio ones before 1.0 (#249), so a map still holding an acoustic graph loads neither in 1.0 nor in 2.0: re-save it from the Hammerite that wrote it with its audio rebaked, or rebuild it;
  • a node carries a 1.x script on a node the scene does not make itself (an instance's, or an inherited scene's), or one whose class the native one does not extend: set the node's type in the Godot editor;
  • a binary scene (.scn) places a node by its 1.x script: save it as a .tscn from the Godot editor, and run the migration again.

A script of the game's that extends one of Hammerite's by path (extends "res://addons/hammerite-core/...gd") is the game's code, not a resource, and is not touched: extend the class by name.

2.0 ships without the 1.x compatibility layer its development builds had - a stub script at each 1.x path and a loader that read 1.x files as the native classes (#272) - and the migration needs neither: it knows each 1.x script by the path and the uid 1.x gave it. It ships with every 2.x release (API stability).

The entity interface

Core's scene nodes are native (#268): HammeriteMap3D, the entity bases, and every entity class of core's own sets. A game's entity class still extends a base (HammeritePointEntityNode3D, HammeritePointEntityAnimatableBody3D, HammeritePointEntityRigidBody3D, HammeriteBrushEntityNode3D, HammeriteBrushEntityStaticBody3D, HammeriteBrushEntityAnimatableBody3D, HammeriteBrushEntityArea3D) or one of core's entity classes, but it overrides the interface under the engine's convention: a method a script overrides is a native virtual, and a native virtual is a name with an underscore. The public names stay, and are what everybody calls - the map, the editor, a game: each dispatches to the virtual.

Rename every override to its underscore name. The signatures are unchanged.

An override left under its old name does not compile: it would hide a native method the engine calls, which GDScript refuses (Required virtuals).

super() goes. GDScript cannot call super() into a native virtual, nor super._init(), super._ready() or super._process() on a native class. Where an override called super() first - set_entity, update_properties, apply_entity_property on one of core's classes, get_actions, run_action - the class's own now runs first by itself, and the script's override after it, so drop the call:

# 1.x
func set_entity(new_entity: HammeriteEntity) -> void:
    super(new_entity)
    _offer_a_hand()

# 2.0
func _set_entity(new_entity: HammeriteEntity) -> void:
    _offer_a_hand()

Work an override did before super() has to find another place: it runs after the base now. A flag raised around super() to quiet _apply_entity_property while the entity is being bound starts raised instead, and _set_entity lowers it. get_actions()'s override answers only the actions it adds. Any other override replaces what the class does, as before - with no super() to reach what it replaced. A script on one of core's own classes that called super._process(delta) drops it: the class does its per-frame work from its notification, after the script's _process.

Overriding one of a script's virtuals is unchanged: a class extending a game's entity script still calls super._apply_entity_property(...).

A native class of core's has hooks of its own under the same convention: a script on a dynamic light overrides _get_lit_modulation() and may follow set_seen() with _set_seen(); one on a logic entity or a mover _get_icon(), _tick(), _reset(), _apply() and _wired_targets(); one on HammeritePropModel may follow set_room_seen() with _set_room_seen(); one on HammeriteThumbnailGenerator takes over _generate_thumbnail(), _generate_entity_thumbnail() or _generate_mesh_thumbnail().

A classname may name a native class. HammeriteMap3D builds an entity's node from a script class of that name or, where there is none, from a class the library registers; core's own (HammeritePointLight3D...) are native.

Required virtuals

1.x marked what a subclass had to write @abstract, and a script that left one out did not compile. A native class has no @abstract: what a script must write is a required virtual, and every one of them has an underscore.

1.x, @abstract 2.0, required virtual
set_editor_active(active) and apply_entity_property(prop_name, value) on HammeritePointEntityNode3D, HammeritePointEntityAnimatableBody3D, HammeritePointEntityRigidBody3D, HammeriteBrushEntityNode3D and HammeriteBrushEntityStaticBody3D _set_editor_active(active) and _apply_entity_property(prop_name, value), on those and on HammeriteBrushEntityAnimatableBody3D
apply_entity_property(prop_name, value) on HammeriteBrushEntityArea3D _apply_entity_property(prop_name, value); _set_editor_active is optional there, as set_editor_active was
HammeriteEditorTool's _tool_input(event), _tool_process(delta), _tool_exit() and get_tool_name() _tool_input(event), _tool_process(delta), _tool_exit() and _get_tool_name()
HammeritePropertyControl's get_value(), set_value_no_signal(value), set_disabled(disabled) and set_indeterminate(indeterminate) _get_value(), _set_value_no_signal(value), _set_disabled(disabled) and _set_indeterminate(indeterminate)
HammeriteDynamicLight3D._icon() none: the class is registered abstract, and only its own point, spot and directional lights extend it. A script that extended it extends HammeriteDynamicPointLight3D or one of the others, whose icon is theirs
- HammeriteEntitySet._register_types(), new since 1.0

A script overrides one by declaring it under that name with the signature in the class reference, as it would any engine virtual (func _set_editor_active(active: bool) -> void:). Where the public method of the same name is still what everybody calls, the class dispatches to the override.

One left out is an error when it is called, not when the script compiles. A script extending a base without _set_editor_active parses, and new() makes one where the @abstract script refused; the first call then reports

ERROR: Required virtual method HammeritePointEntityNode3D::_set_editor_active must be overridden before calling.

and does nothing - an engine error, which fails a suite. HammeriteMap3D still refuses a classname whose class does not extend a base, so a map never builds a base itself. The entity suites of a game should build every type it registers and call these once, which is what Hammerite's own do.

One written under its old public name does not compile:

Parse Error: The method "set_editor_active()" overrides a method from native class "HammeritePointEntityNode3D". This won't be called by the engine and may not work as expected. (Warning treated as error.)

The editor

The level editor is native (#271): every class of hammerite-editor, and the editor tools and extensions of hammerite-audio and hammerite-nav, in the library's editor, audio_editor and nav_editor modules, which only the full package has. They keep their names and what they do - each was held to its script, call for call and node for node, before the scripts were deleted - and the shapes that change are the same as core's. What a game that extends or drives the editor changes:

A tool overrides the underscore names. The editor calls tool_input(event), tool_process(delta) and tool_exit(), and get_tool_name(), get_status_text(), holds_cursor() and get_manual_page() as before; each dispatches to a virtual, which is what a script overrides, as an entity does. The editor's three scenes are gone: scenes/ui/property_editor.tscn, scenes/3d/vertex_gizmo.tscn and scenes/3d/transform_gizmo_3d.tscn. Each class builds the same nodes itself: HammeritePropertyEditor.new(), HammeriteVertexGizmo.create(editor) and HammeriteTransformGizmo3D.new() where a game instanced the scene.

The autoloads are thin scripts over native classes. HammeriteAudio is scripts/hammerite_audio.gd, one line extending HammeriteAudioAutoload, and HammeriteNavigation scripts/hammerite_navigation.gd extending HammeriteNavigationAutoload: the same paths and uids, so a project.godot naming them is unchanged, and the same members, which the reference documents. HammeriteEditor stays a script, and makes the editor's classes by name so that it compiles in a game installed without the editor: its editor and workspaces are typed Control, and integrate() answers one. Assign it to a HammeriteMapEditor to have it typed.

var map_editor: HammeriteMapEditor = HammeriteEditor.integrate(self)   # as in 1.x; a cast now, not a type

The migration knows the editor's scripts. The editor's scripts are deleted: a 1.x scene or resource naming one does not load until it is migrated, and tools/migrate_to_2.sh rewrites it. It places each of the 60 editor scripts whose class is a Node (the three scenes' scripts among them) as its native class, and writes the four Resources a user's settings were saved as - HammeriteEditorWorkspace, HammeriteMapEditorSettings, HammeriteGrid and HammeriteEditorColors - as theirs. The audio and nav editor scripts are RefCounted, which no scene places. A library without the editor (the runtime package) has none of those classes, so a file naming one is reported skipped, with its classes and that the full package migrates it, rather than failed. The autoload scripts stay where they were and are left alone.

Defaults are never shared instances. The engine takes a class's defaults from one instance it keeps, so a property a constructor filled was everybody's default, and the Godot editor printed "Instantiated ... used as default value" for each as it opened. HammeriteMap.probe_set is null until the map has one - once it is lit, or read from a file that has one - and a map made with HammeriteMap.new() and saved writes no probe set where it wrote an empty one. HammeriteMapEditorSettings.colors is null until an editor uses the settings; an editor's own always have them. HammeriteMapEditor.settings is made the first time it is asked for.

The shapes that change

A static variable becomes a pair of static methods, get_<name>() and set_<name>(value): GDScript reaches no static property of a native class.

HammeriteDataFile.last_error            # 1.x
HammeriteDataFile.get_last_error()      # 2.0
HammeriteSkybox.dome_material = sky     # 1.x
HammeriteSkybox.set_dome_material(sky)  # 2.0

A constant that is not an integer becomes a static method of its name in lower case: ClassDB binds only integer constants and enums. Integer constants and enums are unchanged (HammeriteBrush.VolumeType.AIR, HammeriteMap.BakeState.BAKED, HammeriteCarving.PLANE).

HammeriteDataFile.MAP_EXTENSION         # 1.x
HammeriteDataFile.map_extension()       # 2.0

A const of your own made from one is a constant expression no longer, since a method call is not: make it a static var or a literal.

const BASE: String = HammeriteReferences.BASE              # 1.x
static var BASE: String = HammeriteReferences.base()       # 2.0

The same goes for a match pattern, which has to be a constant: match the value itself (&"rotation").

A coroutine cannot be a native method. HammeritePrefab.generate_thumbnail() and HammeritePrefabSet.regenerate_all_thumbnails() were coroutines; awaited, they answer as they did:

await prefab.generate_thumbnail(generator)        # true once preview_texture is set, as in 1.x
await prefab_set.regenerate_all_thumbnails(generator)

The lightmapper's bake(), quick_bake(), prepare(), transfer() and write_lightmaps() were coroutines too, and are awaited as before:

var lightmapper := HammeriteLightmapper.create(map, settings)   # new(map, settings) in 1.x
lightmapper.yield_to = get_tree()
if await lightmapper.bake(progress) == OK:
    HammeriteDataFile.write(map, path)

They run on a stack of their own on the main thread and give yield_to a frame where the script awaited one. What they answer is their answer when they never had to wait for a frame, and otherwise the signal HammeriteLightmapper.finished(result), which carries it. Their return type is Variant.

Not awaited, what the prefab methods answer is a Signal to await - HammeritePrefab.thumbnail_generated(has_thumbnail) and HammeritePrefabSet.thumbnails_regenerated() - while a generator that is a coroutine is still drawing, and the answer itself when it answered at once.

A script that extends a native class still does, and still overrides its virtuals; but it cannot call a bare virtual on an object that does not override it, so a native class with one binds a public method that calls it (HammeriteEntitySet.extend_editor(editor) for _extend_editor).

Containers are shared, as a script's were. A getter answers the object's own array or dictionary, typed as before, so changing it in place is changing the object - entity.properties[&"name"] = "x" works as it did. A typed array or dictionary of a moved class is typed by the class's name now, not by its script: get_typed_class_name() answers &"HammeriteBrush" where get_typed_script() answered the script.

Behaviour

  • A moved class has no script. get_script() is null, and get_class() answers the class's own name rather than its native base's. is HammeriteMap works as before.
  • Every bake made before this reads STALE once, and wants baking again, if its map has a sky. A sky's part of the lighting fingerprint (HammeriteMap.lighting_fingerprint(), which get_bake_state() compares with the one a bake recorded) was every stored property of the skybox, by name and in its script's order, the script's own uid and path among them - so renaming colour to color dated every bake there was, though nothing lit had changed. It is now what the bake reads of the sky, worked out as the lightmapper works it out, in a fixed order under a tag that says which line it is (sky2|...): what a sky aperture emits (ambient_color() in linear colour times light_energy), whether that light claims a slot of its own and with which group (light_is_dynamic, light_group), and - only when a directional light the bake reads follows the sky - the sun's direction, colour and energy. A rename, a property added, the sky's name, its model and where it is seen from, a game's own sky properties and a sun nothing follows date no bake from now on; a change to what the bake reads of the sky still does, and changing what it reads changes the tag. The brushes' and entities' parts of the fingerprint, and the program fingerprint, are unchanged to the bit, so a map with no sky reads as it did.
  • HammeriteEntitySet is a virtual class: HammeriteEntitySet.new() succeeds where the @abstract script refused, and a set with no _register_types fails when it is added.
  • HammeriteEntitySets.any_name and the other providers can no longer be passed as a Callable value from GDScript: GDScript cannot make a Callable of a native static method.
  • The registries convert some bad values where the scripts raised a script error: String() of a non-string _editor_rotation_axes, bool() of a null or a string casts_shadow/bake_static, float() of a non-number clarity.
  • HammeriteBrush.volume_type and interior_exterior are 32-bit enums: a file holding a value beyond 32 bits reads back as another. Only absurd values are affected.
  • The data file keeps GDScript's typed-member refusals when reading a class that was a script: a value of the wrong type leaves the member alone rather than being converted, so old files read as they did.
  • HammeriteAABBGrid.query_after with after below -1 no longer answers -1.
  • HammeritePrefab and HammeritePrefabSet: a 1.x .tres or .res of a prefab or a set, its array typed by the prefab's script, is migrated to the native classes.
  • HammeriteBakeOccluder.from_mesh reads a surface of an ArrayMesh that has no index array straight through, as it always said it did; the script stopped on a script error there and answered null.
  • HammeriteTerrain.convert of a brush whose top has no corners is an error and answers no prisms, where the script stopped on a script error. HammeriteTerrain.of() answers a plain null for a brush that is not terrain, which compares as the script's did.
  • A Resource of a moved class opened in the Godot editor runs its constructor there now: a new HammeriteMap made in the inspector has its default layer.
  • Property docs: an inspector reading a class's ## comments out of its script (HammeritePropertyDocs) has no script to read for a moved class; its words are in the class reference, Godot's own help.
  • Speed: nothing answers differently, but sooner. The compile benchmark's 256 rooms compile in 303 ms rather than 626, and a one-brush edit in 25 rather than 42; the persist benchmark's largest loads from a .res in 113 ms rather than 220.
  • A null an entity's signal hands on - HammeriteTrigger.fired(by) with nobody, HammeriteMap3D.map_changed with no map - is a plain null, as the scripts' was.
  • map_3d.gd and eye_adaptation_3d.gd are gone: a 1.x scene that names them by path is migrated to name the class (type="HammeriteMap3D"), as a scene saved since does.
  • hammerite-nav's classes are native (#270): the ground, the links, the profiles and their table, the report, the brush properties, the floor's edges, the cache, the mesh writer, the runtime and the link entity, in the library's nav module, and the overlay the Navigation tool draws in its nav_editor module, which only the full package has. The HammeriteNavigation autoload, HammeriteNavigationTool and HammeriteNavigationEditorExtension followed with the editor (The editor). A table of profiles or a .nav.res 1.x saved is migrated to the native class. A navigation cache 1.x saved is taken up as it was: every fingerprint is worked out to the byte as the scripts worked it out, and a .nav.hcache the native classes save is the scripts' file byte for byte.
  • A .nav.res cache comes back without its report's warnings, as in 1.x: a resource keeps no array typed inside a dictionary, and the report takes its warnings only as an Array[String], as the script's member did when set by name. Assigning an untyped array to HammeriteNavigationBakeReport.warnings leaves it as it was, where the script raised an error.
  • Navigation is built in half the time or less (HammeriteNavigationRuntime.prepare()): a Thief mission's 5.7 s is 2.8 s, a smaller one's 1.5 s is 0.56 s. Reading a saved cache costs what it did, most of it the fingerprint and the data file.
  • hammerite-audio's classes are native (#269), in the library's audio module, HammeriteEnvSound and HammeriteEnvSoundEnvironment as native subclasses of HammeritePointEntityNode3D. The HammeriteAudio autoload, HammeriteAudioPortalTool and HammeriteAudioEditorExtension followed with the editor (The editor).   • A native audio class has no script to read its property docs from (HammeritePropertyDocs): its words are in the class reference.
