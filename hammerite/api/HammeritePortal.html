Hammerite 3D API reference

HammeritePortal

Core: the map. Inherits Resource

A derived portal joining two air HammeriteCells in the subtractive world model.

A portal exists between two air brushes when they share a face OR intersect; the portal is the boundary of the shared region. There is no separate stable portal id: a portal is identified by the unordered pair of cell ids {A, B} (plus a small discriminator if the two brushes touch in more than one disjoint region). Everything that references a portal (audio edge, per-portal override, lightmap adjacency) keys on that pair, which survives a nudge - only the portal polygon changes shape.

Property descriptions

cell_a

var cell_a: int = 0

The two air-brush ids this portal joins. Stored min-first (see make_key()) so the pair is canonical regardless of author order.

cell_b

var cell_b: int = 0

The higher of the two air-brush ids this portal joins; see cell_a.

region_a

var region_a: int = 0

Which REGION of each brush this portal actually joins. A brush split by a structural wall has several rooms in it, and an opening leads into one of them - so a consumer that wants "the room on this side" needs the region, not just the brush.

region_b

var region_b: int = 0

The region of cell_b's brush this portal opens into; see region_a.

region

var region: int = 0

Discriminator among the portals joining this brush pair. Two rooms sharing a wall with two windows in it get two portals, 0 and 1, separately addressable. Assigned by the compiler in a canonical geometric order, so it stays with the same opening across an edit.

polygon

var polygon: PackedVector3Array = PackedVector3Array()

Convex polygon of the opening (world space, ordered loop). Empty on an overlap portal - see is_aperture().

plane

var plane: Plane = Plane(0, 0, 0, 0)

Plane the portal polygon lies on, as the wall of host_face's room: its normal points out of that room, which may be either side. A zero Plane() on an overlap portal.

host_face

var host_face: HammeriteFace = null

One of the two authored HammeriteFaces this aperture was punched from, if any (lineage - texture / uv_transform / lightmap_scale flow from here in later phases). Which room's face it is follows brush iteration order, NOT cell_a. Null on an overlap portal, which has no aperture and therefore no face - see is_aperture(), and null when the wall came from a clip rather than an authored face.

host_face_b

var host_face_b: HammeriteFace = null

The opposite, coplanar source HammeriteFace, on the other room's side from host_face. An aperture is punched from a PAIR of faces, one per room, and which of the two is "a" falls out of brush iteration order rather than anything an author can see. Consumers that read authored data off the host face must therefore check both, or naming a doorway would work or not depending on which room was drawn first.

Method descriptions

make_key()

static func make_key(a: int, b: int, discriminator: int = 0) -> Vector3i

Canonical dictionary key for a portal joining cells a and b with the given region discriminator: Vector3i(min(a, b), max(a, b), discriminator). Keep portal-key construction in this single place so every consumer (audio edges, per-portal overrides, lightmap adjacency, HammeriteMap's own portal index) agrees on the key shape.

key()

func key() -> Vector3i

This portal's canonical key, as make_key(). Stable across a recompile as long as the two brushes and the order of their openings are.

region_key_a()

func region_key_a() -> Vector2i

The region key (HammeriteCell.key()) of the room on side A.

region_key_b()

func region_key_b() -> Vector2i

The region key (HammeriteCell.key()) of the room on side B.

other_region()

func other_region(region_key: Vector2i) -> Vector2i

The room on the far side of this portal from region_key, or a zero key when the given room is not one of its two sides.

is_aperture()

func is_aperture() -> bool

True when this portal is a real APERTURE - a hole in a shared wall, with a polygon and a plane. The other kind is connectivity-only: two air brushes that interpenetrate have no aperture between them at all, because there is no wall there to make a hole in. They are one continuous open space, which is why the boundary-wall holing skips them and why they cannot be named.

property_key()

func property_key(field: StringName) -> StringName

Key for one of this portal's authored values on its host face: portal/<cell a>/<cell b>/<discriminator>/<field> - the portal's own key(), then the field. The whole key, because one authored wall can host several openings. The discriminator only counts the openings joining one PAIR of rooms: a hall and a corridor joined by two doorways resolve both portals to the same face, and so does a room wall with a doorway into one neighbour and a window into another, which are both opening 0 of their pair. Keyed by anything less, naming one would name the other. Consumers put their own values under their own field names; the key shape lives here so they agree on it. The cost is that the key names the two rooms by brush id, so an opening of a room that becomes a new brush - copied, or clipped in two - starts out unnamed. And the discriminator falls out of where the openings are (see HammeriteSubtractiveCompiler.compile_portals()), so cutting a third opening between the same pair that sorts ahead of the others shifts the indices and the authored values with them. Moving geometry - by far the commoner edit - does neither.

adopt_legacy_properties()

static func adopt_legacy_properties(portals: HammeritePortal[]) -> void

Move values stored under the key maps were saved with before property_key() carried the pair, portal/<discriminator>/<field>, onto the key each opening has now. That key could not tell apart the openings on one face that lead to different rooms, so where only one opening on the face has that discriminator the value is its, and where several do it was all of theirs - each showed it - and each keeps it. A value no opening on its face claims is left where it is, for an opening that comes back to find.

get_portal_name()

func get_portal_name() -> String

The author's name for this opening, or "" if it was never named. A portal's name is the one identity every consumer shares. A window is a route for navigation and a hole for sound, and it is the same window - naming it twice, once per addon, would let the two disagree about which opening a door entity means. So the name lives HERE, on the portal (which is to say on the authored face beneath it), and the addons read it.

set_portal_name()

func set_portal_name(portal_name: String) -> bool

Name this opening, writing through to the face the aperture is punched from. Returns false when there is no face to write to - an overlap portal is not an aperture and cannot be named (is_aperture()). An empty name clears the property rather than storing a blank, keeping the face's storage sparse.

clear_face_property()

func clear_face_property(prop_name: StringName) -> void

Erase prop_name from BOTH host faces. Both, because an aperture is cut from a pair of them and either may be carrying the value: a name written to one side earlier must not survive as a ghost when the author clears it from the other.

get_face_property()

func get_face_property(prop_name: StringName, default = null) -> Variant

The authored value of prop_name taken from whichever host face carries one, or default. host_face wins a disagreement, but only because something has to.

property_host()

func property_host(prop_name: StringName) -> HammeriteFace

The face an authored value for prop_name should be WRITTEN to: whichever host face already carries one, else host_face. Null on an overlap portal, which has no face to write to.
