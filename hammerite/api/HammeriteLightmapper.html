Hammerite 3D API reference

HammeriteLightmapper

Core: lighting. Inherits RefCounted

GPU-accelerated lightmap baker for Hammerite brush/BSP levels.

Overview - Converts static brush faces into lightmaps using a multi-pass radiosity solve. - Pass 0 computes direct lighting and assigns up to 4 most influential lights per face. - Subsequent passes propagate bounced (indirect) light using patch radiosity "unshot". - Per-face patches store energy in RGBA, where each channel is a light slot (0..3). - Optional water/transmission produces per-slot caustics accumulated in a parallel RGBA atlas. - Low‑res chroma transfer (CT) is baked per texel and encoded rank‑1 (tint + weights). - Faces are grouped by light coverage, packed into atlases, and UV2 is updated in-place. - Produces HammeriteBakedLightmap resources bound to faces and light entities for the runtime. Pipeline (high level) 1) initialize_lightmaps(progress_cb) - Collect faces/lights from HammeriteMap. - Unwrap faces into lightmap texture space via HammeriteLightmapPacker. - Build a temporary per-face reflectance cache (locks albedo images). - Subdivide faces into texel-aligned patches (+1 patch pad against seams). - Release reflectance cache image locks. 2) light_transfer(bounce_count, progress_cb) - For N passes (default 4): • compute_light_pass(0): direct light + choose up to 4 per-face light IDs. • compute_light_pass(1..N-1): bounce passes using previously unshot energy. Assign any new per-face light IDs if bounced to new faces. - GPU computes per-patch radiosity, per-slot caustics, and per-slot color-transfer vectors. - HammeriteLightmapperState keeps the transient GPU buffers and decoded results between passes. 3) update_lightmap_textures(progress_cb) - Group faces greedily by their assigned light IDs (<=4) to minimize atlas count. - Swizzle per-patch radiosity channels to match each group’s canonical slot order. - Pack grouped faces into atlas images; create matching empty ImageTextures. - Write per-patch radiosity into atlas pixels; also write caustics into a parallel RGBAF image. - Compute chroma transfer per texel (rank‑1): T (RGB) and K (RGBA), and write to low‑res atlases. • CT_Tint: RGB8, sRGB import; CT_Weights: RGBA8, linear; resolution 1/downscale (default 1/2). - Optional per-face antialias in-rect to soften seams for thin/diagonal geometry. - Build HammeriteBakedLightmap resources (color + optional caustic + CT textures) and assign: • To lights that influenced the atlas (for debug/metadata). • To every face in the atlas (via HammeriteFace.set_lightmap). Chroma Transfer (CT) details - Goal: cheap, coherent color bleeding. - GPU accumulates per-texel, per-slot transfer vectors C_s (RGB), s ∈ {0..3}. - Rank‑1 factorization per texel: • T = normalize(Σ C_s) (shared chroma/tint) • K_s = dot(C_s, T) / (dot(T,T) + ε) (per-slot scalar weights) - Runtime reconstruction in brush.gdshader: • sumL = Σ (light_colors[s] * K_s * light_modulation[s]) • chroma = T * sumL; added to base_lit and caustic overlay. - How much of it SHOWS is ct_gain on the material (HammeriteBrush.chroma_bleed, and the editor's Colour bleed knob): the blend from a surface's own colour towards the bleed colour. Nothing baked depends on it, so it moves without a re-bake. It was a hardcoded 0.2 for the blend plus an inert multiply on the chroma vector - inert because only that vector's DIRECTION survives, so any scalar on it cancels exactly. - Storage & sampling: • ct_tint_texture: RGB8 sRGB (Godot import as sRGB), filtered with mips. • ct_weights_texture: RGBA8 linear, filtered with mips. • Resolution is reduced by HammeriteLightmapPacker.color_transfer_downscale (default 2 → half res). Data model (selected) - Patch: per-texel cluster within a HammeriteFace; stores radiosity, unshot, reflectance, caustic, area, ct0..ct3. - HammeriteLightmapperState: transient bake state; faces, patch arrays, GPU buffers, per-face light IDs, lit flags. - HammeriteLightmapPacker: unwraps faces and packs them into atlases; also computes normalized UV2 for faces. - HammeriteLightmap: an atlas “bin” containing faces and up to four HammeriteLightmapLight references (slot order 0..3). Key conventions and limits - Up to 4 lights per face; channel layout is RGBA → slots 0..3 consistently across the pipeline. - Textures are floating-point (RGBAF) during bake; output lightmaps are ImageTexture created from Image. - Reflectance is sampled from the face albedo at the patch center using face planar UVs. - Transmission/caustics come from the brush, never the texture's name: a water fill, or a brush entity with "water", at its "clarity". A face's texture only decides per texel how much of that gets through, by its alpha. - Default atlas size is _texture_size (Vector2(512,512) unless overridden when constructing the packer). Dependencies - gpu_lightmapper.glsl compute shader (resources/gpu_lightmapper.glsl). - HammeriteLightmapperState for buffer packing/reading and per-pass chaining. - HammeriteLightmapPacker for unwrap/group/pack and UV2 updates. - A progress_cb Callable(stage: String, current: int, total: int) to surface progress to the editor UI. Typical editor bake order - initialize_lightmaps → light_transfer → update_lightmap_textures → update_probe_lights.

Enumerations

enum FalloffMode

ValueNameDescription
0INVERSE_SQUAREWhat light actually does: brightness falls with the square of the distance, and so never quite reaches nothing. Energy is luminous flux in lumens.
1LINEARA stealth game's light: a straight ramp from the lamp to a hard edge at falloff_range, and darkness past it. Not what light does, but what a level made of dark and light needs - see the note on falloff_range. Runs hotter than INVERSE_SQUARE within the range and nothing at all outside it, so a map changing modes retunes its lamp energies.

GATHER_PART_SIZE

const GATHER_PART_SIZE = 512

How many patches a probe asks about in the first part of the gather; the parts after it are sized from how fast the one before went. A part used to be a sixteenth of a probe's cells, as long as the probe was dense: a probe of the reference level reads six hundred thousand patches, and a sixteenth of one kept a thread of a GTX 1070 Ti busy for two seconds, where Windows resets the GPU. Nor is staying under that enough: a slice is only as short as its slowest thread, so a thread must take a fraction of SLICE_SECONDS for a slice to hold more than a few hundred of them and the GPU to be anything like full. A thread of the 1070 Ti asks about a patch every fifty microseconds or so, so this is some twenty-five milliseconds there.

FULL_SLICE

const FULL_SLICE = 32768

Enough invocations in one submit to keep a large GPU busy: a part whose slices come out smaller asks too much of each thread, and the next is made smaller.

MOST_PER_PART

const MOST_PER_PART = 8192

The most a part of the gather or a bounce may ask of one probe, however quick the GPU.

BOUNCE_PART_SIZE

const BOUNCE_PART_SIZE = 64

How many senders a probe asks about in the first part of a bounce. A sender is any probe of the map, and the ray to one across it is long: a thousand of them kept a thread of the 1070 Ti busy for a second.

LIGHTS_PER_PART

const LIGHTS_PER_PART = 64

How many lights the direct pass asks about in one dispatch. A texel of the reference level with seven hundred lights to ask was alone longer than the second Godot waits for a submit.

SLICE_SECONDS

const SLICE_SECONDS = 0.1

How long one submit of a pass should run. Godot gives up waiting for a submit after a second on Metal ("timeout waiting for fence") and reads back whatever is there - a whole pass over the reference level ran for minutes and baked nothing - and Windows resets a GPU that is busy for two. A tenth of that leaves room for the next slice's texels to cost ten times what these did.

SLICE_TIMED_OUT

const SLICE_TIMED_OUT = 0.95

Near where Godot stops waiting: a submit that took this long may have been read back unfinished.

FIRST_SLICE

const FIRST_SLICE = 256

The first slice of a pass, before its cost is known. A texel of the direct pass on the reference level costs a GPU thread a third of a second, so a slice takes that long however few it holds - slices grow from small, as far as their time allows, rather than being cut down from a guess.

DRAIN_ATTEMPTS

const DRAIN_ATTEMPTS = 120

How many seconds' worth of backlog _drain() waits out before carrying on regardless.

WASTEFUL_MIN_TEXELS

const WASTEFUL_MIN_TEXELS = 4096

How many of a face's own texels must be unlit before its lightmap is atlas spent on black, and how many texels it has to hold before that is worth saying. A small face is not where an atlas goes, and a wall with a lit corner is doing its job - what this is for is the big surface nothing reaches, which costs as much to light as the one in the middle of the room.

WASTEFUL_DARK_FRACTION

const WASTEFUL_DARK_FRACTION = 0.9

The share of a face's texels that must be unlit, from 0 to 1, for WASTEFUL_MIN_TEXELS to apply.

WASTEFUL_DARK_RADIANCE

const WASTEFUL_DARK_RADIANCE = 1e-05

Under this a texel is not dim, it is unreached: nothing accumulated into it at all, and the threshold is there for float noise rather than to draw a line between dark and darker.

Property descriptions

enable_diagnostic_report

var enable_diagnostic_report: bool = false

Write a detailed per-pass report of the bake to a text file in HammeriteLightmapperDiagnosticReport.DEFAULT_DIRECTORY, and every atlas beside it as a PNG, for debugging the lightmapper itself. Off, because a bake is not something that should leave files behind unasked.

bake_report

var bake_report: HammeriteLightmapBakeReport = null

Lean, in-memory, per-pass energy report (HammeriteLightmapBakeReport), always built and left available after the bake so tests and debugging can assert on the static+dynamic, patch+probe energy flow between passes - the thing the verbose _diagnostic_report (dynamic-only, patch-only, write-to-file) cannot show. Rebuilt at the start of each light_transfer(). Cheap: pure CPU aggregation over data the per-pass readback already decoded.

bounce_scale

var bounce_scale: float = 1.0

How much of the bounce is kept, as a fraction of what the physics says. 1.0 is now literally physically based, rather than aspirationally so: every transfer in the bake is a form factor - cos * cos * area / (pi * d^2) - and reflectance is applied by whoever sends, so the numbers the passes carry are light rather than units of their own. This is the one knob over them, applied ONCE where the direct pass seeds its unshot energy, and it is the only place indirect intensity is decided. The default is 1.0, which is to say: bake what the light actually does, and reach for this knob when a room wants opening up or shutting down. What makes that defensible is ALBEDO. A closed box of reflectance a returns about a/(1-a) of its direct light, so stone at linear 0.1 gives some 12% and shadow stays shadow; it is only a room made of white paper that fills in, and levels are not made of white paper. Turn it DOWN for a darker game rather than turning the lights down: indirect is what softens a room, and a stealth game wants direct light bold and indirect soft, because shadow has to be somewhere a player can stand. 0.15 is roughly where this toolkit sat while the bake was still carrying units of its own. It moves the INDIRECT and nothing else, which it did not always. Probes used to sit out the direct pass and take only what they gathered off the patches, so a probe's value was the bounce alone - and this knob scaled every reading the game takes off HammeriteMap.light_level_at(), the light gem and the guards' eyes among them. Sharpening shadows with it blinded them, invisibly, because the luxels kept their direct light and the picture hardly changed. Probes take the direct pass now, so this does what it says: bold shadows from the direct light, and as much or as little soft fill on top as a level wants.

emission_scale

var emission_scale: float = 8.0

Multiplier on emission texel values. The texture is LDR, so its brightest texel is 1.0, while a point light's irradiance on a nearby surface runs to tens - this is the knob that decides how bright "fully white in the emission map" actually glows. Raise it for lamp glass and lava, lower it for faint runes.

shadow_samples

var shadow_samples: int = 4

How many visibility rays a luxel casts at each light, spread over the texel's own footprint. One ray, from the middle of the texel, makes a shadow a yes-or-no per texel: the edge lands on the lightmap grid and stair-steps along it, which no amount of filtering afterwards can undo, because the half-lit texels were never computed. Four samples across the texel give it the part-lit texels it should have had. Costs what it says: four times the visibility rays of the direct pass. Static rather than per-instance because the shader reads it out of the shared params buffer, which HammeriteLightmapperState packs without an instance to ask.

water_reflections

var water_reflections: bool = true

Whether a pool throws the light that falls on it back into the room over it (#79). The surface is flat, so the bake reflects each light off it as an image source, and the ripples focus what they bounce as they focus what they let through. Off is the bake as it was before that, which is what a map wants when the reflection is more than it can afford - it is a second pair of visibility rays per light, per texel, per pool. Static for the same reason shadow_samples is: the shader reads it out of the shared params buffer, which HammeriteLightmapperState packs without an instance to ask.

water_refraction

var water_refraction: bool = true

Whether light entering water bends where it goes in: Snell's law at the surface, for the texels and the probes under it. Off is the straight line from light to receiver, which puts lit patches and shadow edges on a pool floor where the light does not reach and misjudges how bright it is there. Static for the same reason shadow_samples is.

falloff_mode

var falloff_mode: int = 0

Which FalloffMode the direct pass uses. Static for the same reason shadow_samples is: the shader reads it from the params buffer, packed without an instance to ask.

falloff_range

var falloff_range: float = 8.0

How far a LINEAR light reaches, per unit of its energy: a lamp of 32 with the default 8.0 lights 256 units around itself and nothing beyond. The reason a mode with an end to it exists at all: an inverse-square lamp is never actually out of range, so a wall right across the level takes a small but real amount of light from it - enough to wash out a room meant to be dark, and enough to spend one of the four light slots that wall has on a lamp nobody would say was lighting it. Bounces then carry that further. A range makes both questions answerable by where the lamps are.

bounce_range

var bounce_range: float = 0.0

How far bounced light carries, in world units, or 0 for as far as it can see. The direct pass having an end to it is only half the job. What a lit wall throws is light in its own right, and with no range on it a bright courtyard keeps feeding a cellar three rooms away through the small contributions of a hundred distant patches - the same flood by another road. A room or two is the useful setting; the light that should reach further is a lamp's job.

bounce_floor

var bounce_floor: float = 0.0

How faint a switchable light's bounced light may be before a wall goes without it, as a light level, or 0 to keep all of it. Bounced light never falls to nothing, and a wall that takes any of a switchable light's holds one of its four slots for it and is packed with the walls that light reaches: a level of a few hundred such lights had nearly every wall holding four, in thousands of atlases, most for light nobody would see. A baked light's bounce costs a wall nothing and is all kept.

sky_lightmap_scale

var sky_lightmap_scale: float = 64.0

The texel size of a sky aperture's lightmap, which nothing ever renders - it exists only so the aperture has patches to emit from. Coarse on purpose: a courtyard's whole ceiling at wall resolution would be most of the atlas, spent on a texture no eye will meet.

probe_gather_radius_mult

var probe_gather_radius_mult: float = 12.0

How far a probe reaches for the patches that light it, as a multiple of the probe grid's cell size (64 units), so 12 is 768 units. This is a hard cutoff applied BEFORE the visibility ray, not a falloff - the form factor's inverse square already handles distance - so a patch beyond it contributes nothing at all rather than contributing a little. At the old 3 (192 units) that meant a probe could only be lit by the bounce off surfaces within about a room's width of it, and anything further away simply did not exist. In a large room, most of the room is further away. Measured on a 768-unit room with a sun through a sky face: 2.2% of direct came back as bounce at 3, and 8.1% at 12, against the ~11% that albedo 0.1 predicts. The same room lit by a point light instead reads 1.7% at 3 - this was never about the sun, it was about the size of the room. It is not free: what it admits is more visibility rays in the gather. At these sizes the bake time did not move measurably; on a large level it will, and this is the knob to bring down if it does.

yield_to

var yield_to: SceneTree = null

Set, a bake that is awaited gives this tree a frame every YIELD_MS or so - between GPU submits, and between faces - so an editor can draw its progress and take a Cancel. Unset, a bake runs straight through and need not be awaited.

cancelled

var cancelled: bool = false

Stops a bake that yields at its next chance, leaving whatever it had written: the caller knows what was there before it and puts that back (see HammeriteMap.snapshot_lighting()). A bake stopped this way cannot be continued; start the next one from initialize_lightmaps(). The caller clears it again. light_transfer() sets it too when this process cannot bake (see can_bake()), so a caller that puts the old lighting back on a cancel does so then as well.

cull_buried_prop_faces

var cull_buried_prop_faces: bool = true

Whether a prop's triangles that face rock close by are left unlit (HammeriteMeshTriangleData.buried). They are a share of every prop that stands on a floor or against a wall, and each was unwrapped, given room in an atlas and lit, for nobody to see.

native_texels

var native_texels: bool = <unknown>

Whether faces are cut into texels by the native kernel (#116), into exactly the rows _subdivide_face() makes. True when tools/build_native.sh has installed it (see HammeriteNative); the suites turn it off to check one against the other.

native_atlas

var native_atlas: bool = <unknown>

Whether a face's texels are written into its atlas by the native kernel (#116), which fills and filters exactly the pixels write_face() does. True when tools/build_native.sh has installed it (see HammeriteNative); the suites turn it off to check one against the other.

Method descriptions

caustic_water_color()

static func caustic_water_color(water_sums: Vector3) -> Color

What one texel stores about the water its caustics came from: its disturbance in red, its depth over CAUSTIC_WATER_DEPTH_RANGE in green. A texel no caustics reached is black, and has no caustic intensity for the shader to shape with it either. water_sums is disturbance sum, depth sum and weight - see Patch.water_sums().

dilate_caustic_water()

static func dilate_caustic_water(image: Image, rect: Rect2i, passes: int = 4) -> void

Carry the water at the edge of a region of caustics out into the texels around it that none reached, within rect. Blue marks a texel that has a value; what is written out is marked too, so the next pass carries it further. The texels outside the caustics hold no water - black - and a linearly filtered sample at the edge blended toward that: disturbance and depth both fell to zero across the last texel, so the pattern's speed and size changed over a few pixels, and changed fastest exactly where the caustics fade out. What the value is out there does not matter, since there are no caustics there to shape; that it is the same as just inside is what matters.

can_bake()

static func can_bake() -> bool

False under the Compatibility renderer, on the web and in a --headless run: a bake dispatches compute shaders on a RenderingDevice, and those have none. A map baked elsewhere still displays there.

quick_bake()

func quick_bake(progress_cb: Callable = Callable()) -> int

Lights the faces that have no lighting - the walls an edit has moved, cut or made since the last bake - by direct light alone, and leaves the rest as they are: the other walls, the props and the probes. A face a bake has already left dark is not tried again (HammeriteMap.dark_surfaces). Only the lights that can see one of the faces take part, and only the rock and brushwork around them and those lights shadows them. Each bake adds atlases of its own, which the next full bake packs together again. The bake stays as out of date as it was (see HammeriteMap.store_partial_bake()). Returns how many faces it lit; when it was cancelled, the caller puts the lighting back.

initialize_lightmaps()

func initialize_lightmaps(progress_cb: Callable = Callable()) -> void

Unwrap and pack faces into lightmaps Generate as many lightmaps as required to fit every face.

light_transfer()

func light_transfer(bounce_count: int = 4, progress_cb: Callable = Callable()) -> void

Step 2 of a bake, after initialize_lightmaps(): the direct pass, then, when bounce_count is above 0, a gather into the probes, bounce_count - 1 probe-to-probe bounces and a distribute back onto the texels. 0 is direct light only. Creates and frees its own local RenderingDevice; where there is none it reports an error and sets cancelled. Rebuilds bake_report. Awaitable; see yield_to.

compute_light_pass_chunked()

func compute_light_pass_chunked(pass_index: int, total_passes: int, progress_cb: Callable, stage: String, progress_current: int, progress_total: int) -> void

Runs pass pass_index a slice of the texels at a time, reporting progress_current of progress_total under stage as it goes. Only valid inside light_transfer(), which owns the RenderingDevice it dispatches on.

compute_light_pass()

func compute_light_pass(pass_index: int, total_passes: int, progress_cb: Callable = Callable(), stage: String = "") -> void

Runs one pass of the transfer. The gather and the bounces are the long ones, and report how much of what the busiest probe has to ask is asked, as stage, to progress_cb.

pack_faces()

func pack_faces(progress_cb: Callable = Callable()) -> void

Pack faces into lightmap textures.

write_face()

static func write_face(images: Image[], texels: HammeriteLightmapPatches, rows: Vector2i, black: HammeriteLightmapPatches, black_rows: Vector2i, bounds: Rect2) -> PackedInt32Array

Write a face's texels - rows of texels, as (first row, count) - into its atlas's images, and its black_rows of black over them, then filter the images within bounds, where the face was packed. The images are the atlas's radiosity, caustics, chroma tint, chroma weights, static light, static caustics and caustic water, in that order; the last is not filtered. Returns how many of the texels are lit, and 1 if any took caustics from water.

update_lightmap_textures()

func update_lightmap_textures(progress_cb: Callable = Callable()) -> void

Step 3 of a bake, after light_transfer(): groups and packs the faces into atlases (see pack_faces()), writes the textures, and assigns them to every baked face and prop. Records the bake's warnings and baked surfaces on the map and notifies its views. Call update_probe_lights() after it. Awaitable; see yield_to.

update_probe_lights()

func update_probe_lights() -> void

The last step of a bake, after update_lightmap_textures(): tone-maps each lit probe's radiosity in place and appends the HammeriteBakedLights that reach it, then tells the map its probes are baked. Call it once per bake - it appends, so a second call doubles each probe's lights and tone-maps twice.

class BakedDecal

A decal that opted into the bake, reduced to what a patch has to ask of it: where it is, and what its picture says at a point.

Reading the images once and holding them is the same trade the per-face reflectance cache makes - a patch centre is tested against every decal, and get_image() per test would decompress a texture per texel.
